# OpenWiki

The project's wiki is generated by OpenWiki directly into `<project>/openwiki/`, the CLI's default code-mode output directory. That same directory is the native GitHub Wiki's separate Git repository. There is one set of pages, not a source tree copied into a second publishing clone.

## Durable decisions

- Run locally using the saved ChatGPT-subscription login. Set `OPENWIKI_PROVIDER` to `openai-chatgpt` and `OPENWIKI_MODEL_ID` to `gpt-5.6-luna` for every run. If unavailable, report the error and ask before switching models.
- Use explicit `code` mode from the main project root. The default output is `<project>/openwiki/`; no custom output-directory support or CLI modification is required. Personal mode at `~/.openwiki/wiki` is unrelated.
- Keep `/openwiki/` ignored by the main repository. Include it in the project's `.gitignore` for portability even when the global Git ignore already covers it. Wiki pages belong to the Wiki repository, not the main repository or a submodule.
- Publish to the native GitHub Wiki, not MkDocs or GitHub Pages. Generate directly in the clone and commit/push there; no second documentation tree or copy-to-publish step.
- Regenerate page content through OpenWiki unless the user explicitly requests manual edits. Publication may normalize filenames and links in place.
- Keep OpenWiki generation local-only. Remove OpenWiki CI workflows newly recreated by a run; preserve unrelated workflows and report any pre-existing OpenWiki CI configuration before changing it.

## Where things live

| Location | Purpose |
| --- | --- |
| `<project>/openwiki/` | The only generated documentation tree and the GitHub Wiki clone; `Home.md` is the published entry page |
| `openwiki/INSTRUCTIONS.md` | Local generation prompt, excluded from Wiki publication |
| Generation metadata under `openwiki/` | Local generator state, excluded from Wiki publication |
| `<!-- OPENWIKI:START/END -->` blocks in project `AGENTS.md` / `CLAUDE.md` | OpenWiki-maintained references to `openwiki/`; review changes in the main repository separately |
| `~/.openwiki/.env` | Provider/model configuration and ChatGPT OAuth tokens |

Treat values in `~/.openwiki/.env` as secrets. If inspection is necessary, read variable names only; never print, copy, or commit values. Exclude the generation prompt and internal state through the Wiki clone's `.git/info/exclude`, using the actual files produced by the installed version. Preserve those files locally across updates.

## Generate or update

For a missing clone or a legacy layout, follow [references/setup.md](references/setup.md) before generation.

1. Verify that `openwiki/` has its own Git repository and its `origin` is this project's `<repo>.wiki.git`. Checking Git from inside an ordinary directory can resolve the parent repository, so confirm the Git top-level is exactly `openwiki/`. For existing generated docs without a Wiki clone, follow the setup reference's migration section rather than replacing them.
2. Preserve pending changes in either repository. With a clean Wiki clone, pull its rendered branch using `--ff-only` before updating; stop on divergence rather than overwriting it.
3. From the main project root, run `openwiki code --update --print` with the provider/model from the durable decisions and the default output directory. Use `--init` instead of `--update` for first generation. Do not run from inside the Wiki clone, which would document the wrong repository.
4. Review status, `diff --check`, and the full diff in both repositories. Confirm pages and state changed only under `openwiki/`, no second documentation tree appeared, and agent-file references point to `openwiki/`. Apply the local-only CI rule.

Done when all changes are explained, Wiki Git metadata is intact, and the main repository contains no generated Wiki pages. Generation alone is not publication; continue below when syncing to GitHub is requested.

## Sync with GitHub Wiki

Prepare the generated pages in place inside `openwiki/`:

- Preserve established page names. On first generation, normalize the entry page to `Home.md` and flatten other names into a single namespace, such as `Architecture-overview.md`. Resolve filename collisions explicitly rather than overwriting a page.
- Give every published content page one `_Sidebar.md` entry. Exclude the generation prompt and internal state.
- Use flattened page names without `.md` for internal links, preserving anchors. Links to main-project files must be absolute `https://github.com/<owner>/<repo>/blob/<branch>/...` or `tree/...` URLs.
- Keep generation instructions consistent with the final page names so later runs update these same pages rather than creating duplicate source pages.

Review and stage only the intended page changes in the Wiki clone. Run `git -C openwiki diff --cached --check` and inspect the staged diff before committing. Commit only if it changed, then push the Wiki's actual rendered branch; discover it rather than assuming `master`. A rejected push is a blocker, not permission to force-push. Do not stage or commit the main repository as part of Wiki synchronization.

Done when each generated content page has one published page and sidebar entry, internal links resolve in GitHub's flattened namespace, the Wiki clone's `HEAD` and remote rendered branch agree, and the Wiki tab renders `Home` with its sidebar.
