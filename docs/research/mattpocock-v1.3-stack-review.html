Why all three earn a place

retroAdd first

The clearest missing capability. Your stack can review a diff, diagnose a bug, and propose architecture improvements. It cannot currently audit a session's tool usage, missing information, ineffective instructions, or unwired checks as a dedicated workflow.

Use it on a troublesome session or a small sample of recent sessions. Its output should be a ranked set of proposals. Mechanical mistakes belong in deterministic checks; judgment calls can become review standards. Keep execution safety visible to the implementation agent.

Keep it user-invoked. Approve changes individually, rather than letting it continuously rewrite its own environment.

prAdd

Improve the review input, not the review process. Your implement asks for a clear summary and validation list, but does not define a consistent explanation of the change, observed before/after behavior, and merge risk.

The new skill supplies that format. Let it own the body, while implement owns PR creation, ticket references, validation, target branch, and readiness. Keep commit responsible for Git closure.

implement-specAdd

A distinct execution scale. Your implement works tickets one at a time. implement-spec orchestrates the ready frontier of an entire ticket graph across isolated worktrees, then brings the work together on one integration branch and reviews the combined diff.

This is complementary to single-ticket implementation, not a duplicate and not a reason to remove it. Add it as a user-invoked route for approved, multi-ticket specs. Installation does not mean every small task should use it.

Share your approved requirements and TDD rules with workers. Keep integration-based branching, final combined validation, and aggregate PR ownership in the orchestrator.

Do not invoke your local implement wholesale inside each worker: it branches from the repository default and creates its own ready PR. Reuse the relevant policy, not an incompatible close-out sequence. Pin seams in the approved tickets so workers do not invent decisions or repeatedly ask the same questions.

What to remove, update, and prune

Retire resolving-merge-conflicts

The release explicitly removes it with no replacement. Your 14-line copy mostly describes ordinary Git work, but adds unconditional "never --abort" and "stage everything" instructions. Those commitments are not justified for every conflict. Preserve both sides' intent and validate the result as ordinary task-specific Git work.

Retirement must remove the catalog and updater entries, the router reference, and managed installed copies. Stopping synchronization alone does not remove a skill.

Fix review coverage before adding more ceremony

Your implementation close-out reviews before committing, but code review uses git diff <fixed-point>...HEAD. That command reviews commits, not outstanding working-tree changes. It can miss the implementation it was asked to review.

Keep the two-axis review. Define a working-tree mode covering tracked and relevant untracked changes, and pass a resolved comparison point from the caller. This is a static instruction inconsistency, not a measured session failure.

Migrate the glossary as one coherent change

Update glossary producers and consumers together, including customized setup and its domain.md template, the router, diagnosis, architecture guidance, triage, and supporting references. Rename existing project domain files deliberately; do not rename every unrelated file called CONTEXT.md.

The updater downloads files but does not prune upstream deletions. It also skips customized skills and tracks main without a release ref. Neither obsolete format files nor customized old-name writers will disappear merely because update.py ran.

Shorten TDD's common path, preserving its requirements

Your TDD entry file is 401 lines; tagged v1.3.1 is 38. Size alone is not a verdict, but the local file repeats end-to-end policy in several sections and makes non-UI work read detailed UI-only guidance.

Keep the common RED/GREEN loop, agreed seams, command timeouts, explicit failures, and final end-to-end gate in the entry file. Put extended examples and UI-specific reference behind clear pointers. Have implement refer to this canonical policy instead of restating it. Preserve real-browser behavior checks and desktop defaults.

Make cross-skill loading and browser routing consistent

The tiny grilling wrappers still name /grilling in prose. Port v1.3's explicit-loading fix using each tool's real mechanism. Pi reads the skill file; a nonexistent Skill tool is not a valid instruction.

repo-visualizer and TDD contain their own browser-tool preference lists. Prefer a pointer to the required browser-harness workflow so tool choice, ownership, and cleanup stay consistent with your global policy.

Resolve presentation and scope contradictions

  • Prototype. Your global policy asks for all UI options on a self-contained comparison page. The UI prototype reference prefers switching between variants on one route. Align it with your preferred comparison format without changing the mock-before-real-components rule.
  • To spec. "A LONG" and "extremely extensive" user-story lists can inflate a small feature. Ask for complete coverage of the agreed requirements, not length for its own sake.
  • To tickets. Keep requirement traceability, verified parent/blocker relationships, and change propagation. Remove obsolete local-tracker branches from the active path if GitHub-only remains your chosen setup. Offer both execution routes at handoff.
  • Ask Matt. It still mentions the old glossary, local tracker, retired conflict skill, and diagnosis post-mortem handoff. Align it with the actual stack and make summaries orientation, not substitutes for reading skill definitions.

Refine instructions rather than deleting their useful purpose

Keep unslop's plain-language discipline and codebase-design's shared vocabulary. Their absolute language rules can be too rigid: punctuation bans can hurt technical explanation, and banning "component" or "API" everywhere is not appropriate when those are the subject's actual names. Apply architectural vocabulary to architectural discussion; preserve exact code and domain terminology.

Keep operational safety, authorization, secret handling, shell correctness, and resource cleanup in global instructions. Disclose detailed style guidance on demand. These are recommendations for later approval, not changes to your existing preferences.
